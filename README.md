# AI-Powered Customer Support System

A fullstack, multi-agent customer support platform. Users sign in with Google, shop a small product catalog that generates **real** orders and invoices, and chat with an AI support system that routes each message to a specialized agent — support, orders, or billing — backed by live database queries. Responses are generated by an LLM (Groq or xAI Grok) and streamed to the UI, with every conversation persisted per user in PostgreSQL.

---

## Overview

This project demonstrates an agentic AI backend integrated with a clean, responsive React frontend, built around real-world engineering concerns: authentication and per-user data isolation, multi-agent orchestration, database-backed and **action-capable** tools, LLM-generated responses with a factual-accuracy guard, live streaming UX, and persistent conversation state.

Unlike a typical demo, the data is not faked: buying a product in the in-app Store creates an order and a paid invoice, orders progress through fulfillment, and refunds run a full lifecycle — and the agents answer questions (and take actions) against that real data.

## Architecture

```
Google Sign-In (Firebase)
     │  Firebase ID token attached to every request
     ▼
requireAuth middleware → verifies token, derives userId (never trusts client)
     │
     ├──────────────► Store API ──► orders / invoices / refunds  (real data)
     │                                        │
     ▼                                        ▼
POST /api/chat/messages                 PostgreSQL (per-user)
     │                                        ▲
     ▼                                        │
Router — reference patterns → keywords → LLM fallback
     │
     ├── Support Agent   → conversation history
     ├── Order Agent     → order + product + tracking data
     └── Billing Agent   → invoices, refund status, AND files refunds
                │
                ▼
     Draft answer (authoritative DB facts)
                │
                ▼
     LLM rewrite + reference-accuracy guard  → streamed to client
                │
                ▼
     Saved as assistant turn
```

1. Users authenticate with Google; the frontend attaches the Firebase ID token to every API call.
2. The backend verifies the token and derives `userId` server-side — clients never send it.
3. The router classifies the message via reference-number patterns, then keywords, then an LLM fallback.
4. The matched sub-agent queries (or mutates) the database through its tool layer.
5. The DB-backed draft is rewritten by the LLM, validated for reference accuracy, and streamed back.
6. The response is persisted as an assistant message in the user's conversation.

## Key Features

### Authentication & per-user isolation

Firebase Authentication with the **Google provider only** (no email/password). The API verifies the ID token with the Firebase Admin SDK and derives the user from it, so a client can never read or act on another user's data. All `/api/chat` and `/api/store` routes require a valid token.

### Real commerce data (in-app Store)

A Store tab turns the app from a mock demo into a real workflow:

- **Buy** a product → creates an `Order` and a paid `Invoice` in one transaction (payment simulated; a Stripe checkout can slot in here).
- **Fulfillment** → advance an order `PROCESSING → SHIPPED` (assigns tracking + ETA) `→ DELIVERED`.
- **Refunds** → request a refund, then progress it `REQUESTED → APPROVED → COMPLETED`, marking the invoice `REFUNDED`.
- **Delete** orders (with their invoices/refunds) when you're done.

The seed script only populates the product catalog — every order, invoice, and refund comes from a real user action.

### Multi-agent routing (three layers)

1. **Reference patterns** — `ORD-…`/`INV-…` numbers route deterministically regardless of phrasing.
2. **Word-boundary keywords** — expanded vocabulary, no substring false positives (`billboard` ≠ `bill`); a refund concerning an order routes to billing.
3. **LLM fallback** — ambiguous messages are classified by the model instead of blindly defaulting to support.

### Action-capable, database-backed agents

Each sub-agent queries real data, and the billing agent can also **take actions**.

| Agent | Capabilities |
|---|---|
| Support Agent | Queries prior conversation history for context |
| Order Agent | Fetches order + product details, delivery status and tracking; lists all orders |
| Billing Agent | Retrieves invoices and refund status; **files refunds** against an order's paid invoice, with guard rails (unknown order, no paid invoice, no double-filing) |

### Reference-accuracy guard

The LLM rewrites a DB-backed draft into a friendly reply, but any order/invoice/tracking number it produces that is **not** present in the draft or the user's message is rejected, and the factual draft is used instead. Hallucinated reference numbers — including ones leaked from earlier conversation turns — structurally cannot reach the user.

### Conversation management

- LLM-generated thread titles (instead of the raw first question)
- Inline **rename** and **delete** from the sidebar
- Threads persist across refreshes; the last 8 turns are passed to the model so follow-ups keep context

### Streaming UX

Responses stream to the UI in real time, with an animated thinking indicator in the pending assistant bubble. Agent replies can include links (e.g. "visit the Store") that deep-link to the right tab.

## API Reference

All `/api/chat` and `/api/store` routes require an `Authorization: Bearer <Firebase ID token>` header. `userId` is derived from the verified token, never sent by the client.

### Chat

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/chat/messages` | Send a message and stream the assistant response (SSE) |
| `GET` | `/api/chat/conversations` | List the user's conversations |
| `GET` | `/api/chat/conversations/:id` | Fetch a conversation with its message history |
| `PATCH` | `/api/chat/conversations/:id` | Rename a conversation |
| `DELETE` | `/api/chat/conversations/:id` | Delete a conversation |

### Store

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/store/products` | List the product catalog |
| `POST` | `/api/store/checkout` | Buy a product (creates an order + paid invoice) |
| `GET` | `/api/store/orders` | List the user's orders with invoices and refunds |
| `POST` | `/api/store/orders/:id/advance` | Advance fulfillment (ship → deliver) |
| `POST` | `/api/store/orders/:id/refund` | File a refund request |
| `POST` | `/api/store/orders/:id/refund/advance` | Progress a refund (approve → complete) |
| `DELETE` | `/api/store/orders/:id` | Delete an order and its invoices |

### Agents & Health

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/agents` | List available agents |
| `GET` | `/api/agents/:type/capabilities` | Get capabilities for a specific agent |
| `GET` | `/api/health` | Health check |

## Local Setup

### Prerequisites

- Node.js 20+
- npm 10+
- PostgreSQL 16 (local via Docker, or a hosted database such as Neon)
- A Firebase project with Google sign-in enabled

### Environment

Copy the templates and fill in the values:

```bash
cp .env.example .env                 # root (used by the API)
cp apps/web/.env.example apps/web/.env
```

API / root (`.env`):

```env
DATABASE_URL="postgresql://user:pass@host:5432/db?schema=support"
# AI provider — set ONE. Omit both for deterministic fallback streaming.
GROQ_API_KEY=""      # keys start with gsk_ (default model llama-3.3-70b-versatile)
XAI_API_KEY=""       # keys start with xai- (default model grok-3)
AI_MODEL=""          # optional model override
PORT="3000"
# Firebase Admin (Project settings → Service accounts → Generate new private key)
FIREBASE_PROJECT_ID=""
FIREBASE_CLIENT_EMAIL=""
FIREBASE_PRIVATE_KEY=""   # one line, literal \n for newlines, quoted
```

Web (`apps/web/.env`):

```env
VITE_API_BASE_URL="http://localhost:3000"
# Firebase web config (Project settings → your web app) — public client keys
VITE_FIREBASE_API_KEY=""
VITE_FIREBASE_AUTH_DOMAIN=""
VITE_FIREBASE_PROJECT_ID=""
VITE_FIREBASE_APP_ID=""
```

> **AI provider:** both providers are called through their OpenAI-compatible endpoints (no extra SDK). Groq takes priority if both keys are set; override the model with `AI_MODEL`. With no key, the backend streams the deterministic DB-backed draft.

### Firebase (Google sign-in)

1. In the [Firebase console](https://console.firebase.google.com), create a project and a **Web app**.
2. Under **Authentication → Sign-in method**, enable **Google**.
3. Copy the web config into `apps/web/.env` (public client keys — safe in the browser bundle).
4. Under **Project settings → Service accounts → Generate new private key**, put the JSON values into the API `.env`. **These are secrets — never commit them.**
5. `localhost` is authorized by default; add your production domain under **Authentication → Settings → Authorized domains** when you deploy.

### Installation

```bash
npm install

# If using local Postgres via Docker:
docker compose up -d

npm run db:generate     # generate the Prisma client
npm run db:push         # sync the schema
npm run db:seed         # seed the product catalog

npm run dev             # start API + web
```

The apps run at:

- API: `http://localhost:3000`
- Web UI: `http://localhost:5173`

## Try It Out

1. Open the web UI and **sign in with Google**.
2. Go to the **Store** tab and buy a product — this creates a real order and invoice.
3. (Optional) Use **Ship order** / **Mark delivered** to advance fulfillment, or **Request refund** to start a refund.
4. Switch to **Chat** and ask about it:

| Prompt | Routes to |
|---|---|
| `list all my orders` | Order Agent |
| `where is my latest order?` | Order Agent |
| `show my latest invoice` | Billing Agent |
| `request a refund for ORD-…` | Billing Agent (files the refund) |
| `what's my refund status?` | Billing Agent |
| `I need help with my account` | Support Agent |

Responses stream in progressively; conversations persist in the sidebar, where you can rename or delete them.

## Engineering Highlights

- Google authentication with server-side token verification and per-user data isolation
- Real commerce data: orders, invoices, and a full refund lifecycle from real user actions
- Three-layer router (reference patterns → keywords → LLM fallback)
- Action-capable agents backed by real database queries, with guard rails
- Reference-accuracy guard so hallucinated order/invoice numbers never reach the user
- LLM-generated conversation titles; rename, delete, and persistent threads
- Provider-agnostic LLM streaming (Groq / xAI) with a deterministic fallback
- Controller–service separation, typed errors via a single `onError` hook
- Shared Zod schemas between frontend and backend via a monorepo package
